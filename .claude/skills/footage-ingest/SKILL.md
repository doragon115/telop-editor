# 撮影素材をパイプラインに載せる

長尺の撮影素材を telop-editor で扱える形にするまでの導線。

この工程は、放っておくと**運搬で何時間も溶ける**。実際に、17分・2.61GB の動画を運ぶのに
半日かけかけた例がある。そのとき本当に必要だったのは **16MB の音声だけ**だった。
このスキルの主目的は、その種の浪費を最初の5分で防ぐこと。

## 最初に問うこと：本当は何を運ぶ必要があるのか

**運ぶ前に、行き先が何を消費するのかを確認する。** ここを飛ばすのが最大の失敗要因になる。

telop-editor は **元の映像を使わない**。Remotion の構成に動画レイヤー（`OffthreadVideo`）が無く、
`Audio`（音声）と `Img`（静止画）だけで組み立てている。確認するなら:

```bash
grep -rn "OffthreadVideo\|<Video" src/
```

何も出なければ、映像は使われていない。**つまり運ぶべきは音声だけで、動画本体は要らない。**

| 運ぶもの | 17分の素材でのサイズ | 1.5Mbps 回線での所要 |
|---|---|---|
| 動画（1080p） | 2.6 GB | **約4時間** |
| 音声（mp3 128kbps） | **16 MB** | **約2分** |

160倍の差になる。**この確認だけで、たいていの運搬問題は消える。**

素材の縦横や尺を先に知りたいときは `npm run cut -- 素材.mp4 probe` で分かる（元動画が手元にある場合）。

## 所要時間の見積もり方

「遅い」で止まらず、必ず数字にする。判断が変わる。

```
所要秒数 = バイト数 × 8 ÷ 回線速度(bps)
```

回線速度は Google 検索の「インターネット速度テスト」で測れる。
**アップロードとダウンロードは別物**なので、送る側の数字を使うこと。

見積もりが30分を超えるなら、その経路は選ばない。もっと小さいものを運ぶ方法を探す。

## 経路の選び方

上から順に試す。上ほど速く、失敗しにくい。

| 経路 | 向いている場面 | 注意 |
|---|---|---|
| **SDカードを抜いてリーダーへ** | カードに保存されている | 回線を一切使わない。最速 |
| **音声だけ抜いて送る** | 動画が大きい・回線が細い | **迷ったらこれ。16MBなら何で送っても通る** |
| USBケーブルで直結 | ケーブルがデータ対応 | 充電専用ケーブルが紛れている事故が多い |
| 同一LAN内の直接転送（LocalSend等） | 大きいまま運びたい | インターネット速度とは無関係に速い |
| クラウド（Googleフォト等） | 小さいファイル | 大きいと往復で二重に時間を食う |

素材のパスが `/storage/XXXX-XXXX/` のような形なら、それは**SDカード**なので抜ける可能性がある。
`/storage/emulated/0/` なら内部ストレージなので抜けない。

## USBで認識しないとき

**先に時間の上限を決める。10分試して駄目なら音声ルートへ移る。** ここは粘っても報われにくい。

順に潰す。上ほど頻度が高い。

1. **スマホ側のUSBモードを「ファイル転送」にする** — 初期状態は「充電のみ」で、切り替えないとMacから中身が一切見えない。通知をタップするか、設定 → 接続済みのデバイス → USB
2. **スマホのロックを解除する** — ロック画面のままだと見えない
3. **OpenMTP の MTP Mode を Legacy にする** — 歯車 → General。既定の Kalam は対応機種が狭い。切り替わるとウィンドウのタイトルが `Legacy Mode` に変わる
4. **USBを掴んでいるアプリを終了する** — Googleドライブ、Android File Transfer、Dropbox が干渉する
5. **ケーブルを疑う**

### ケーブルの切り分け

これが決定打になる。Macがスマホを**電気的に見えているか**を確かめる。

```bash
ioreg -p IOUSB -w0 -l | grep -i "USB Product Name"
```

繋いだ状態で実行し、**スマホらしい名前が出ないなら、そのケーブルは充電専用**（データ線が入っていない）。
ポートや端子の故障の可能性もあるが、原因としては充電専用ケーブルが圧倒的に多い。

**重要**: 充電専用ケーブルでも、スマホ側では「ファイル転送」を選べてしまう。
選べたことはデータ線がある証明にならない。ここで混乱しやすい。

メーカー名で絞り込む grep は使わない。`system_profiler ... | grep -i pixel` のような書き方だと、
機種名が想定と違うだけで「何も出ない」となり、**繋がっているのに繋がっていないと誤判定する**。
名前を列挙せず、全件を出して目で見ること。

## 音声だけ運ぶ迂回路

USBを諦めたときの本命。**回線が細くても2〜3分で終わる。**

### スマホ側

1. Playストアで「動画 MP3 変換」を検索し、評価の高い無料アプリを入れる
2. 対象の動画を選んでMP3に変換。**128kbps で十分**（喋りなので音質はこれで足りる）
3. 共有 → Googleドライブ / 自分宛メール / LINEのKeepメモ など、やりやすい方法でMacへ

### Mac側

`npm run cut` は音声ファイルを直接受け取れる。動画である必要はない。

```bash
npm run cut -- ~/Downloads/変換した音声.mp3 --install
```

## ディスクの空きが足りないとき

**元動画が必要なのは最初の1分だけ。** `audio` の段で音声トラックを抜いたら、
以降は `out/silence-cut/source_audio.m4a` から処理するので、元動画は消せる。

```bash
npm run cut -- 元動画.mp4 audio    # 1分ほど
rm 元動画.mp4                       # ここで容量が戻る
npm run cut -- dummy --install      # 続きは元動画を読まない
```

必要量の目安（17分の素材の場合）:

| | 一時的に要る | 残る |
|---|---|---|
| 元動画 | 2.6 GB | 0（消せる） |
| 抜いた音声一式 | — | 0.07 GB |
| whisperモデル（未取得なら） | — | 2.9 GB |
| node_modules（未インストールなら） | — | 1 GB |
| Remotionの書き出しと一時ファイル | 1〜2 GB | 0.5 GB |

macOS は空きが5GBを切ると不安定になる。**最終的には15GB以上を確保しておく。**
モデルの有無で3GB変わるので、まず `du -sh ~/.cache/whisper` で確認する。

## 素材が入ったあとの流れ

```bash
npm run cut -- 素材 --install   # 無音とフィラーを落として input/audio/audio.mp3 へ
npm run transcribe               # テロップの文面を作る
npm run image-timeline           # 挿絵の枠を並べる（図が多いとき）
npm run editor                   # http://localhost:3001 でテロップ調整
npm run studio                   # http://localhost:3000 でプレビュー
npm run render                   # 書き出し
```

詳細は `docs/SILENCE-CUT.md`。カットの詰め具合は `--min-silence` で調整でき、
`cut` の段で止めれば文字起こしをやり直さずに短縮率だけ試せる。

**書き出しは最後に回す。** 12分の縦型は2万フレーム超になり時間がかかるので、
先に Studio で頭の1〜2分を確認してから回すほうが早い。

## 相手が非エンジニアのとき

この工程は、機械の前に座っている人の手を長時間拘束する。次のことを意識する。

- **コマンドは1行ずつ渡す。** まとめて渡すと、どこで失敗したか分からなくなる
- **各コマンドの「成功したときの見え方」を先に伝える。** 「`2612715053` と出たら成功」のように、
  判断基準を渡しておけば、次の質問を待たずに進める
- **画面の位置を具体的に指す。** 「右側のツールバーのいちばん右端の歯車」のように、
  相手が見ている画面の言葉で言う
- **見切る基準を先に共有する。** 「10分試して駄目なら別の手に切り替えます」と言っておくと、
  相手が無駄に粘らずに済む
- **移動中や外出先なら、スマホだけでできることを先に渡す。** パソコンが開けるまで待たせない
